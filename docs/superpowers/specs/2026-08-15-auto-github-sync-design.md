# Codex 自动同步 GitHub 设计

## 目标

为本仓库建立一套持久的 Codex 任务收尾规则。以后 Codex 在本项目中完成文件修改后，应在验证通过的前提下，将本任务改动提交到独立功能分支、推送到 `origin`，并创建或更新面向 `master` 的 Pull Request。

该流程不监控外部编辑器，不自动提交用户手动产生的改动，也不自动合并 Pull Request。

## 适用范围

- 仅适用于 Codex 在本仓库内执行且产生文件修改的任务。
- 回答问题、只读诊断、代码审查或没有产生文件变化的任务不触发同步。
- 用户使用其他工具产生的改动不由该流程后台提交。
- 用户在当前任务中给出的更新、更高优先级指令可以覆盖本规则。

## 持久化方式

在仓库根目录新增 `AGENTS.md`，将自动同步定义为仓库级工作约定。Codex 进入本仓库后读取该文件，并在每个产生改动的任务结束时执行规则。

不采用以下方式：

- 不安装后台目录监控器，避免无上下文地提交临时文件或未完成内容。
- 不使用 Git `post-commit` 钩子，因为它无法负责测试、文件归属隔离和 Pull Request 内容。
- 不要求常驻 PowerShell 进程，避免机器重启、登录状态和进程生命周期影响同步。

## 任务流程

### 1. 建立基线

Codex 修改文件前记录：

- 当前分支与 HEAD；
- 工作树和暂存区状态；
- 已存在的未跟踪文件；
- 远端地址和上游分支。

任务开始前已经存在的改动一律视为用户所有。Codex不得覆盖、恢复、暂存或提交这些改动。

### 2. 选择分支

- 新任务开始时先获取 `origin/master`，再从该远端引用创建 `codex/<简短任务名>` 功能分支；不为此切换或改写本地 `master`。
- 无法获取 `origin/master` 时，不假定本地引用是最新版本；Codex 应暂停并询问用户是否允许基于现有引用继续。
- 分支名仅使用小写字母、数字和连字符；发生重名时追加日期或递增序号。
- 如果用户明确要求继续已有 Pull Request，则沿用对应功能分支。
- 不直接在 `master` 上提交任务改动。
- 不通过自动同步流程强制拉取或改写存在本地修改的分支。

### 3. 实施与验证

Codex完成任务后，根据改动风险运行必要验证：

- 文档和配置改动检查差异、格式及相关静态校验；
- JavaScript 或 Python 改动运行受影响的测试；
- Android 改动运行相关 Gradle 检查、单元测试和所需构建；
- 跨模块或高风险改动扩大测试范围。

测试记录必须来自本任务结束前的新鲜命令结果。未运行的测试不得在 Pull Request 中标记为通过。

### 4. 精确暂存

- 只使用显式文件路径暂存本任务产生的改动。
- 禁止使用会囊括整个工作树的宽泛暂存命令。
- 提交前检查暂存文件列表和暂存差异，确认没有用户既有改动。
- 如果本任务改动与用户既有改动落在同一文件且无法安全拆分，则停止同步并请求用户决定。

### 5. 提交、推送与 Pull Request

- 提交信息使用简洁的 Conventional Commits 格式，例如 `feat: ...`、`fix: ...`、`docs: ...`。
- 推送当前功能分支到 `origin` 并建立上游跟踪。
- 没有现有 Pull Request 时，创建面向 `master` 的 Pull Request。
- 已有对应 Pull Request 时，只推送新增提交并更新现有 Pull Request，不重复创建。
- Pull Request 描述包含修改摘要、实际运行的验证命令与结果，以及已知限制。
- 推送后核对本地 HEAD、远端跟踪分支和 Pull Request 源提交一致。

## 安全边界

同步前检查本任务文件，不提交以下内容：

- API Key、访问令牌、密码、私钥或签名密钥；
- 本地环境文件、缓存、测试临时文件或无意生成的截图；
- 未被项目明确要求跟踪的构建产物；
- 来源或用途不明的超大二进制文件。

项目明确要求版本管理的大型资产只有在其大小、来源、许可证和远端限制均已确认后才能提交。

自动同步不执行以下操作：

- 合并或关闭 Pull Request；
- 强制推送；
- 删除远端或本地分支；
- 清理宿主环境管理的 worktree；
- 改写历史或回退用户提交。

## 失败处理

- 测试、构建或必要静态检查失败：不提交、不推送、不创建 Pull Request，报告失败命令和关键错误。
- 凭据或敏感信息检查失败：停止同步，指出受影响文件但不显示秘密内容。
- 暂存范围无法与用户改动隔离：停止同步并请求用户决定。
- 推送失败：保留本地提交和功能分支，报告远端错误，不进行破坏性重试。
- GitHub 未认证：停在认证步骤，要求用户自行登录；Codex 不读取、保存或代填密码、令牌和验证码。
- Pull Request 创建失败：保留已推送分支并提供可用的比较链接或具体阻塞信息。

## 最终报告

同步完成后的回复应包含：

- Pull Request 链接；
- 功能分支和提交 ID；
- 已运行验证及结果；
- 尚未合并到 `master` 的明确说明。

若流程被阻塞，回复应说明改动当前停留在工作树、本地提交还是远端分支，并给出恢复所需的唯一下一步。

## 验收标准

1. Codex 修改任务在验证通过后自动创建或更新功能分支 Pull Request。
2. `master` 不被自动提交或自动合并。
3. 任务开始前的用户改动不会进入 Codex 提交。
4. 验证失败时不会产生新的远端提交或 Pull Request。
5. Pull Request 中的测试结果与实际执行证据一致。
6. 推送后本地、上游和 Pull Request 源提交保持一致。
7. 只读任务和外部工具产生的改动不触发后台同步。
